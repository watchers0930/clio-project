## 1. 기능 개요

Electron 앱의 OS 로그인 시 자동실행과 주기적 heartbeat를 이용해 일별 출퇴근 시각을 기록한다. 웹앱에 공용 근태관리 화면을 만들고, 직원이 기록을 조회·수동 보정하고 기존 휴가원 양식으로 휴가를 신청하도록 한다. 입사일 기반 표준 연차 부여량과 최종 승인된 휴가를 집계해 잔여 연차를 표시한다.

| 기능 | 핵심 동작 | 적용 환경 |
| --- | --- | --- |
| 자동 근태 | 출근 = 해당 날짜 최초 heartbeat, 퇴근 = 마지막 heartbeat | Electron macOS·Windows |
| 수동 보정 | 본인의 날짜별 출퇴근 시각과 보정 사유 저장 | 데스크탑·웹 |
| 휴가 신청 | 연차·월차·반차·생휴 선택 → 기존 휴가원 생성 → 기존 결재 상신 | 데스크탑·웹 |
| 연차 집계 | 입사일·부여기간·휴가 차감 규칙으로 부여/승인 차감/잔여 계산 | 공통 서버 계산 |
| 관리자 조회 | 전 직원 근태·휴가를 직원 및 기간으로 조회 | 데스크탑·웹 |

웹 브라우저는 조회·보정·휴가 신청을 제공하고 자동 heartbeat는 보내지 않는다. 웹 탭을 켜 두는 것만으로 출근 처리하지 않는다. heartbeat는 앱 생존 기록이며 실제 근로시간·휴게시간·법정 출근율을 판정하는 자료로 단독 사용하지 않는다.

## 4. 기능 상세 요구사항

### 4.1 OS 자동실행 및 heartbeat

- macOS·Windows의 설치된 앱에서 `app.setLoginItemSettings({ openAtLogin: true })`를 적용한다. OS 로그인 시 실행이며 시스템 부팅 시 인증 전 근태 생성과 구분한다. 해당 API의 지원 범위는 [Electron 공식 문서](https://www.electronjs.org/docs/latest/api/app#appsetloginitemsettingssettings-macos-windows) 기준이다.
- 초기 설정은 자동실행 ON으로 제안한다. 데스크탑 설정에서 ON/OFF와 OS에서 조회한 실제 설정값을 표시하고 선택을 재실행 후에도 보존한다. 웹에서는 OS 설정 컨트롤을 숨긴다.
- 개발 실행과 설치 앱을 구분하고 자동실행 등록 실패를 표시한다. Windows NSIS 실행 경로 및 앱 업데이트 후 경로를 검증한다. 단일 인스턴스를 유지해 타이머 중복을 방지한다.
- 기본 전송 간격은 **3분**으로 제안하며 상수로 관리한다. 인증 완료 시 즉시 전송하고 이후 주기적으로 전송한다. 생존 누락 안내 기준은 2회 간격인 6분으로 제안한다.
- 타이머는 Electron main이 관리하고 제한된 preload 이벤트로 공통 `useAttendanceHeartbeat` hook에 tick을 전달한다. 실제 HTTP 요청은 인증 쿠키와 CSRF를 사용할 수 있는 웹 renderer의 동일 출처 fetch에서 수행한다. 서비스 역할 키·세션 토큰을 main/preload 저장소로 복사하지 않는다.
- hook은 AppLayout에 한 번만 연결하며 페이지 이동·재마운트·React 개발 모드에서 구독과 요청 중복을 정리한다. 구독 해제 API도 제공한다.
- 최소화 시 renderer가 멈추지 않도록 백그라운드 throttling 설정과 main tick 전달을 검증한다. OS 절전 중 전송은 보장하지 않으며 복귀 시 즉시 전송한다. 화면 잠금은 앱 생존으로 처리하되 실제 근무 판정에는 사용하지 않는다.
- MVP는 **창 닫기 = heartbeat 중단**으로 정의한다. macOS도 창이 닫히면 타이머·인증 상태를 정리하고 앱을 종료하도록 동작을 통일하는 안을 제안한다. 창 숨김·트레이 상주 방식은 후속 범위로 둔다.
- 명시적 앱 종료 전 마지막 heartbeat를 시도할 수 있지만 성공을 보장하지 않는다. 서버가 이미 저장한 마지막 heartbeat가 기준이다. 강제 종료·전원 종료에는 새 기록을 만들지 않는다.
- 미인증·로그아웃·세션 만료 시 중단하고 재인증 후 재개한다. 계정 전환 시 이전 사용자 타이머와 요청을 폐기한다. 인증 실패를 무한 재시도하지 않는다.
- 네트워크 실패는 지수 backoff로 재시도한다. MVP는 오프라인 신호를 과거 시각으로 일괄 재전송하지 않는다. 서버가 성공 수신한 시각만 기록하고 누락은 수동 보정한다.
- 서버 수신시각을 UTC로 보관하고 근무 날짜는 `Asia/Seoul`로 산정한다. 클라이언트 시간·날짜·user_id를 신뢰하지 않는다. 00:00 이후 heartbeat는 다음 날짜 레코드에 기록한다.
- 사용자·날짜 유일키를 기반으로 DB에서 원자적 upsert한다. 최초 시각은 유지하고 마지막 시각은 증가하도록 처리한다. 여러 기기의 요청도 일별 한 건으로 합친다.
- 한 번만 수신된 날은 최초=마지막으로 저장하고 단일 신호 안내를 표시한다. 신호가 전혀 없는 날은 자동 결근으로 판정하지 않는다.
- 당일 마지막 신호는 '퇴근 기준 시각(갱신 중)'으로 표시하며 신호 단절을 실제 퇴근 확정으로 오인하지 않게 한다. 다음 날에는 전날 마지막 시각을 그대로 표시한다. 별도 정시 퇴근 추정·야간 교대일 묶기는 MVP에 포함하지 않는다.

### 4.2 수동 보정

- 공용 UI에 '출퇴근 보정' 버튼을 제공한다. 본인의 오늘·과거 날짜에 출퇴근 시각과 필수 보정 사유를 입력한다. 신호가 없는 날도 수동 생성할 수 있다.
- 저장값은 원본 `first_heartbeat_at`, `last_heartbeat_at`와 분리한다. 화면의 유효 출퇴근은 보정값이 있으면 보정값, 없으면 heartbeat 값을 사용한다.
- 이후 heartbeat가 도착해도 보정값을 덮어쓰지 않는다. 자동 기록으로 되돌리기도 인증·CSRF가 적용된 명시적 보정 동작으로 처리한다.
- 출근 ≤ 퇴근, 미래 근무일 금지, 보정 시각의 KST 날짜 일치, 사유 길이 제한을 서버에서 검증한다. 자정을 넘는 교대근무는 별도 정책 확정 전 지원하지 않는다.
- 동시 수정은 버전 또는 `updated_at` 검증으로 충돌 응답한다. 변경자·변경시각·이전/이후 값·사유를 기존 `audit_logs`에 기록하며 이력 저장 실패 시 보정 성공으로 응답하지 않는다.
- 관리자 권한은 전체 조회까지이며 임의 대리 수정·삭제 권한은 이번 범위에 추가하지 않는다.

### 4.3 휴가 신청과 기존 문서·결재 재사용

1. 근태관리의 '휴가 신청'에서 본인 정보·휴가 종류·기간·반차 구분·사유를 입력한다.
2. 기존 '새 문서 생성 → 휴가원' 입력 컴포넌트와 생성·미리보기·다운로드 서비스를 재사용한다. 근태에서 진입하면 휴가원과 본인 정보를 미리 채운다.
3. 문서 생성 성공 후 서버가 실제 문서 소유자와 휴가원 종류를 확인해 `leave_requests`와 `documents.id`를 연결한다. 재사용은 단순 링크 제공에 그치지 않고 같은 생성 서비스에 연결 훅을 둔다.
4. 기존 문서 화면에서 직접 생성하는 새 휴가원도 동일한 연결 경로를 거쳐 신청 데이터를 만든다. 기존 자유 입력 기사용일수는 자동 집계값으로 표시하고 차감 원장으로 사용하지 않는다.
5. 상신은 기존 `POST /api/approvals`를 사용한다. 상신 성공 시 실제 `approval_requests.id`를 연결하고 대기 상태를 표시한다. 조직도 상위자 누락으로 실패하면 초안 상태를 유지한다.
6. 중간 단계 승인에는 차감하지 않는다. 최종 승인 또는 전결로 `approval_requests.status = 'approved'`가 되었을 때 차감 대상에 포함한다. 반려는 차감하지 않는다.

휴가 종류는 구조화된 열에 저장하고 기존 휴가원 양식에 종류·반차 표시를 추가하되 기존 결재란·서명·렌더러는 유지한다. 문서 제목이나 AI 출력에서 날짜·종류·차감량을 추론해 저장하지 않는다.

| 종류 | 입력 규칙 | 연차 차감 기본안 |
| --- | --- | --- |
| 연차 | 유효한 근무일 기간 | 근무일당 1일 |
| 월차 | 1년 미만 월 단위 발생분 사용을 의미하는 UI 명칭 | 동일 연차 원장에서 근무일당 1일; 별도 중복 부여 없음 |
| 반차 | 단일 근무일 + 오전/오후 필수 | 0.5일; 입사 1년 미만이면 월 발생분에서도 사용 가능 |
| 생휴 | 단일 근무일, 월별 승인·대기 건 중복 검증 | 0일; 연차와 별도 관리 |

생휴는 근로기준법 제73조의 월 1일 생리휴가를 의미한다. 연차 잔여량으로 신청을 제한하지 않으며 급여 처리는 이번 범위에서 제외한다. [근로기준법 제73조](https://law.go.kr/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=900552022)

- 일수는 회사 근무일 캘린더로 계산한다. 기본안은 월~금에서 법정 공휴일·회사 휴무일 제외이며 단순 날짜 차이를 사용하지 않는다. 캘린더 데이터 제공 방식은 출시 전 확정한다.
- 같은 시간대에 대기·승인된 신청이 겹치면 거부한다. 오전/오후 반차는 각 슬롯을 비교해 서로 다른 반차 조합을 허용한다.
- 승인된 미래 휴가도 요구사항에 따라 즉시 잔여에서 차감하며 화면에는 '승인 차감(예정 포함)'으로 표시한다. 별도로 사용 완료분을 보조 표시할 수 있다.
- 잔여량 경쟁 방지를 위해 대기 중 신청량을 예약량으로 별도 계산한다. `신청 가능량 = 잔여량 - 대기 예약량`이며 신청·최종 승인 시 사용자 단위 잠금으로 재검증한다. 예약량을 승인 차감과 혼동하지 않는다.
- 결재 상태는 기존 `approval_requests`를 권위 데이터로 사용한다. DB trigger 또는 공통 트랜잭션으로 휴가 상태를 함께 동기화하고 조회 시 불일치를 탐지한다. 반복 요청에 차감량을 누적 증가시키지 않고 승인된 고유 신청에서 재집계한다.
- 상신 후 신청자·기간·종류·차감량·연결 문서는 잠근다. 반려 후 재상신은 같은 휴가 신청에 새 결재 건을 연결하고 과거 이력은 기존 결재 테이블에 남긴다.
- 문서 생성/신청 연결/상신의 부분 실패는 재시도 가능하게 만든다. 클라이언트 재시도 키와 `document_id` 유일키로 중복 생성을 막고 연결 실패 문서는 상신되지 않게 서버에서 검증한다.
- 연결된 문서·결재 건의 삭제로 승인 휴가 차감이 사라지지 않도록 삭제를 제한한다. 기존 승인 문서의 수정·버전 생성도 승인된 휴가 데이터 자체를 변경하지 않는다.
- 기존 과거 휴가원은 구조화된 신청값이 보장되지 않는다. 자동 전수 변환하지 않고 출시 기준일 이전 승인 사용분을 담당자가 검증·이관한 후 잔여를 확정한다. 이관 없는 수치는 '집계 시작일 이후'로 구분한다.
- 기존 결재에 없는 승인 취소·철회 절차는 후속 기획으로 둔다. MVP에서 승인된 휴가를 본인이 삭제해 잔여를 복구할 수 없다.

### 4.4 표준 연차 계산

정책 근거는 [근로기준법 제60조](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1025589899)이며 입사일 기준 운영을 기본으로 한다.

- 1년 미만: 1개월 개근마다 1일, 최초 1년 동안 최대 11일.
- 1년 이상: 직전 1년 출근율 80% 이상을 전제로 15일. 만 근속연수 `Y`에 대해 `min(25, 15 + floor((Y - 1) / 2))`로 계산한다. 1·2년 15일, 3·4년 16일, 5·6년 17일, 21년 이상 25일이다.
- 1년 이상이며 출근율 80% 미만인 경우에도 개근 월에 따른 부여 검토가 필요하다. 입사일만으로 해당 조건을 확정할 수 없다.
- 일반 발생분은 부여 후 1년, 1년 미만 월 발생분은 최초 1년 종료일까지의 사용기간을 구분한다. 사용자 귀책 등 소멸 예외는 별도 정책 확인 대상이다.

**MVP 계산값은 개근·80% 출근 요건 충족을 전제로 한 표준값이다.** heartbeat 누락을 결근으로 취급하거나 법정 출근율을 계산하지 않는다. 출근 인정·휴직·단시간근로·계속근로 종료 등 예외 입력이 없으므로 자동 계산을 법정 확정값으로 표시하지 않고 계산 전제를 함께 보여준다. 근로관계·적용대상·예외는 출시 전에 인사 담당자가 확인한다.

`src/lib/leave-policy/`에 부여 구간 생성, 근무일별 휴가 분할, 유효기간별 차감 배분을 순수 함수로 분리한다. 입력은 DB의 `hire_date`, KST 기준일, 정책 버전, 근무일 캘린더, 승인 휴가 내역이다. 출력은 발생일·만료일·발생량·차감량·잔여량 및 계산 근거다.

- `현재 유효 부여량 - 해당 부여 구간에 배분된 승인 차감량 = 잔여 연차`로 계산한다. 입사 이후 모든 휴가를 현재 연차 15일에서 빼지 않는다.
- 만료가 빠른 유효 발생분부터 휴가 사용일에 배분한다. 미래 승인 휴가는 해당 사용일에 유효한 발생분에 배분하고 미래 기간 예약으로 따로 표시한다.
- 입사 기념일·연말을 가로지르는 휴가는 근무일별로 분할해 각 유효 구간에 차감한다. 월차 명칭 때문에 만 1년 도달 시 월 발생분과 새 15일을 중복 합산하지 않는다.
- 입사일 누락·잘못된 날짜·기준일보다 미래 입사일은 계산 불가로 표시한다. 윤년 2월 29일 및 월말 입사자의 기념일 보정 규칙은 정책 함수에 명시하고 인사 확인 후 고정한다.
- 사용량은 0.5일 단위로 계산하고 DB는 `numeric`을 사용한다. 잔여 부족 신청·승인을 거부하며 데이터 이관 등으로 음수가 나온 경우 0으로 숨기지 않고 불일치로 표시한다.
- 입사일 변경 시 서버에서 재계산하고 변경 이력을 남긴다. 과거 승인 문서의 당시 잔여 표시값은 스냅샷으로 유지한다.
- 기존 `computeRemainingLeaveDays`와 미리보기·렌더러 호출부는 같은 정책으로 연결한다. 문서의 `used_leave_days`·`remaining_leave_days`는 서버 집계 스냅샷이며 사용자가 입력한 값을 잔여 계산에 신뢰하지 않는다.

### 5.2 신규 DB 설계안

**`attendance_records` — 사용자별 일별 근태**

| 필드 | 타입/규칙 |
| --- | --- |
| `id`, `user_id` | UUID PK, `users.id` FK |
| `work_date` | KST 기준 DATE, `UNIQUE(user_id, work_date)` |
| `first_heartbeat_at`, `last_heartbeat_at` | nullable TIMESTAMPTZ, 서버 수신 UTC 시각. 수동 생성 시 null 가능 |
| `heartbeat_count` | 성공 수신 수, 0 이상. 감사용 정밀 이벤트 원장은 MVP 제외 |
| `manual_check_in_at`, `manual_check_out_at` | nullable TIMESTAMPTZ, heartbeat 원본과 독립 |
| `correction_reason`, `corrected_at`, `corrected_by` | 현재 보정 사유·시각·사용자. 전체 변경 이력은 `audit_logs` |
| `version`, `created_at`, `updated_at` | 동시 수정 방지·생성/수정 시각 |

날짜/사용자 인덱스와 최초≤마지막, 보정 출근≤퇴근 제약을 둔다. 별도 전체 heartbeat 테이블은 만들지 않고 최초·마지막을 원자 갱신한다.

**`leave_requests` — 구조화된 휴가 및 문서 연결**

| 필드 | 타입/규칙 |
| --- | --- |
| `id`, `user_id` | UUID PK, 신청자 `users.id` FK |
| `document_id` | `documents.id` FK, nullable 초안 연결 전만 허용, 연결 후 유일 |
| `approval_request_id` | 현재 `approval_requests.id` FK, 상신 전 null |
| `leave_type` | `annual / monthly / half_day / menstrual` CHECK |
| `start_date`, `end_date`, `half_day_slot` | DATE 범위 및 `am/pm`. 반차·생휴의 날짜 제약 |
| `requested_days`, `deduct_days` | NUMERIC, 서버 계산. 생휴 차감 0, 반차 0.5 |
| `status` | `draft / pending / approved / rejected`, 기존 결재와 일치 |
| `reason` | 휴가 사유, 길이 제한·접근 제한 |
| `policy_version`, `calculation_snapshot` | 사용 근무일·부여 구간별 배분·계산 기준 보존용 JSONB |

사용자·기간, 상태, 문서·결재 연결 인덱스를 둔다. 날짜 범위·차감량·FK 제약을 적용하며 승인 자료의 참조 삭제는 RESTRICT 또는 동등한 서버/DB 보호로 막는다. 별도 연차 잔액 테이블 없이 신규 두 테이블과 기존 users/결재 데이터를 이용해 집계한다.

### 5.3 RLS·인증·CSRF

- 두 신규 테이블 모두 RLS 활성화. SELECT는 `user_id = auth.uid()` 또는 DB의 `users.role = 'admin'`일 때만 허용한다. `manager`에게 전체조회를 자동 허용하지 않는다.
- 본인 생성은 인증된 서버 API에서만 허용하고 user_id는 인증 결과로 설정한다. 서비스 역할 쓰기를 사용하면 API에서 소유권·활성 사용자·관리자 권한을 먼저 검증한다.
- 브라우저의 직접 INSERT/UPDATE/DELETE는 거부하는 안을 채택한다. authenticated INSERT RLS를 허용하면 CSRF API를 우회하고 승인 상태·원본시각을 조작할 수 있으므로 생성 권한은 API에서 제공한다. 향후 직접 INSERT가 필요하면 필드 제약과 별도 위협 검토가 선행되어야 한다.
- 수동 보정은 본인 행에만 허용하고 휴가 승인 상태·차감량은 결재 서비스만 변경한다. 관리자 전체 조회는 신규 자료에 한정하며 결재자에게 신규 휴가 전체 조회 권한을 확장하지 않는다. 결재자는 기존 문서·결재 권한으로 처리한다.
- 모든 변이 API(POST/PUT/PATCH/DELETE)는 **인증 + CSRF**를 필수로 적용한다. 신규 heartbeat·보정·휴가뿐 아니라 연결 경로의 `/api/generate`, 문서 저장/수정/삭제, `/api/approvals`, `/api/approvals/[requestId]/decide`도 같은 검증을 적용한다. 전 앱 변이 API는 목록을 작성해 공통 가드 적용 여부를 확인하고 미적용 경로를 출시 조건으로 남긴다.
- CSRF는 인증 세션에 결합된 서명 토큰을 발급하고 `X-CSRF-Token` 헤더를 검증하는 안을 사용한다. HTTPS 쿠키 정책과 Origin의 정확한 허용 출처 검증을 병행하며 토큰 없는 요청·잘못된 출처는 403으로 거부한다. Origin 누락을 무조건 허용하지 않는다.
- Electron은 같은 웹앱 URL을 사용하므로 동일 CSRF 흐름을 적용한다. Electron 여부 헤더나 User-Agent를 이유로 CSRF를 면제하지 않는다. GET에는 데이터 변이를 넣지 않는다.
- GET 조회도 인증·소유권 검증하고 타인 id 지정으로 범위를 확장할 수 없게 한다. 개인 응답은 `Cache-Control: private, no-store` 사용, 관리자 조회는 페이지네이션·기간 상한 적용.
- 요청 타입·날짜·열거값·본문 크기를 서버 검증한다. heartbeat 요청에 사용자별 빈도 제한을 두되 정상 다중 기기 요청을 수용한다. 위조한 Electron 신호를 완전히 배제하는 기기 증명은 MVP 범위가 아니므로 보정과 감사가 필요하다.

### 5.4 API 계약안

| API | 역할 | 권한/보안 |
| --- | --- | --- |
| `GET /api/csrf` | 세션 기반 CSRF 토큰 발급, 저장 데이터 변이 없음 | 인증, 캐시 금지 |
| `GET /api/attendance?from=&to=` | 본인 일별 근태 조회 | 인증 + 본인 |
| `POST /api/attendance/heartbeat` | 서버 시각으로 일별 최초/마지막 갱신 | 인증 + CSRF, 본인, 빈도 제한 |
| `PATCH /api/attendance/[workDate]` | 본인 시각 보정/자동값 복원, 미기록일 생성 | 인증 + CSRF + 날짜·소유권·버전 검증 |
| `GET /api/attendance/admin?userId=&from=&to=` | 직원별 전체 근태 조회 | 인증 + admin |
| `GET /api/leave-requests` | 본인 휴가 및 결재 현황 | 인증 + 본인; admin 전체조회는 명시적 범위 검증 |
| `POST /api/leave-requests` | 초안 신청 생성·기존 휴가원 연결 | 인증 + CSRF + 본인 + 멱등키 |
| `PATCH /api/leave-requests/[id]` | 상신 전 초안 수정·연결 재시도 | 인증 + CSRF + 본인 + 상태 검증 |
| `GET /api/leave-requests/balance?asOf=` | 기준일별 발생·차감·예약·잔여 및 근거 | 인증 + 본인; 기준일 범위 검증 |
| 기존 문서 생성·결재 API | 휴가원 생성/상신/승인/반려/전결 | 기존 권한 유지 + 인증 + CSRF 공통 적용 |

응답은 기존 `{ success, data, error }` 방식에 맞춘다. 401 미인증, 403 CSRF/권한 실패, 400 입력 오류, 409 중복·경합·잔여 부족, 503 DB 미설정/일시 장애를 구분한다. 관리자 전용 조회에 일반 사용자 fallback을 두지 않는다.

### 5.5 공용 UI

- 사이드바 `CORE_ITEMS`에 `attendance / 근태관리 / /attendance`를 추가한다. 선택 메뉴의 `sidebar_menus` 목록 수정 없이 전 직원에게 노출되는 기본안이다.
- 상단: 오늘 출근·퇴근 기준 시각, 마지막 heartbeat, 자동 기록 연결 상태, 수동 보정 여부.
- 월별 기록: 날짜·유효 출근/퇴근·자동 원본·보정 표시·보정 버튼. 결근/지각 자동 판정은 제외.
- 연차 카드: 입사일, 계산 기준일, 유효 부여량, 승인 차감, 대기 예약량, 잔여, 신청 가능량 및 계산 전제.
- 휴가 영역: 신청 버튼, 종류/기간/일수/상태/결재 문서 링크. 대기·반려·승인 구분.
- 관리자에게만 전 직원 조회 탭과 직원·기간 필터를 제공한다. UI 숨김 외에 서버 권한 검증을 적용한다.
- 웹에서는 자동 기록이 데스크탑 앱에서 이루어진다는 안내를 제공한다. 로딩·빈 데이터·연결 실패·입사일 누락·잔여 불일치·CSRF 만료 상태를 개별 처리한다.

## 6. 우선순위 및 구현 순서

| 우선순위 | 항목 | 완료 기준 |
| --- | --- | --- |
| P0 — 선행 조건 | 정책·DB·보안 | 월차 의미, 근무일 캘린더, 연차 전제·이관 기준 확정. 신규 테이블 제약/RLS, 공통 인증·CSRF 설계 및 적용 대상 확정 |
| P0 — 필수 | 자동 출퇴근 | 자동실행, 즉시/3분 heartbeat, 공통 hook, 원자 일별 저장, 절전·로그아웃·종료 처리 |
| P0 — 필수 | 공용 UI·수동 보정 | `/attendance`, 핵심 사이드바 메뉴, 원본 보존·감사 이력, 웹/데스크탑 동일 기능, 페이지 500줄 이하 |
| P0 — 필수 | 휴가원·결재 연결 | 네 종류 입력, 기존 생성 진입 두 경로 연결, 상신·반려·전결·최종 승인 동기화, 중복·경합 차단 |
| P0 — 필수 | 연차 자동 집계 | 입사일 표준 계산·장기근속 가산·유효기간 배분, 승인 차감·예약량·잔여 및 문서 스냅샷 일치 |
| P0 — 필수 | 관리자 전체조회 | admin 서버/RLS 검증 및 필터·페이지네이션. 타인 기록 조회 차단 검증 |
| P1 — 안정화 | 상태 안내·복구·관측 | 누락 heartbeat 안내, 부분 실패 재시도, 결재/휴가 불일치 탐지, 운영 이관 검증 |
| P2 — 후속 | 확장 기능 | 트레이 상주·승인 휴가 취소/철회·관리자 대리 보정·교대근무·정밀 출근율 입력·CSV 내보내기 |

구현 순서는 **정책/이관 기준 → 인증·CSRF/DB → heartbeat·보정 → 휴가 연결·연차 계산 → 공용 UI/관리자 조회 → 통합 검증**으로 한다. 모든 요청 기능은 P0이며, P1·P2는 기본 기능 완성 후 확장한다.
