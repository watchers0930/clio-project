# 빌트인 양식 문서 입력값 편집 기획서

- 작성일: 2026-10-23
- 프로젝트: CLIO (`package.json` 기준 v7.82.0, Next.js 16.2.1)
- 상태: 기획 / 구현 전
- 대상: 휴가원·주간업무·재직증명서·업무일지
- 이번 작업 산출물: 본 기획 문서만 작성. 기능 코드·API·DB는 변경하지 않는다.

## 1. 기능 개요

빌트인 양식 문서에서 생성 시 사용했던 입력폼을 다시 열어 입력값을 수정할 수 있게 한다. 현재 원문 편집은 마크다운 본문만 바꾸므로, `DOCUMENT_INPUTS`를 사용하는 서버 양식 레이아웃에는 수정이 반영되지 않는 문제가 있다.

생성 단계의 입력 영역을 공용 컴포넌트로 분리해 생성과 편집에서 재사용한다. 문서 맨 앞의 `<!--DOCUMENT_INPUTS:{...}-->` JSON을 폼 값으로 복원하고, 저장 시 **마크다운 본문은 그대로 유지하고 주석의 입력값만 교체**한다. 기존 `PATCH /api/documents/[id]`에 `{ content }`만 보내고, 성공 후 서버 미리보기를 다시 가져온다.

### 1.1 범위

- `document-viewer-modal.tsx`의 기존 `레이아웃 보기 / 원문 편집` 토글 옆에 `입력값 편집`을 추가한다.
- 대상 양식에서는 입력값 편집을 양식 내용 수정의 기본 경로로 안내한다. 원문 편집은 기존 보조 기능으로 유지한다.
- 초안 상태에서만 편집한다. 완료 문서는 기존처럼 초안으로 되돌린 뒤 편집한다.
- 생성 시의 기본 필드, 조건부 노출, 양식별 특수 UI를 공유한다.
- 신규 API, DB 컬럼, AI 재생성, 본문 재작성, 전체 문서 마이그레이션은 범위 밖이다.
- 품의서·근로계약서·제안서 등 다른 양식의 입력값 편집 확장은 후속 범위다. 공용화에 따른 기존 생성 동작은 보존한다.
- 별도 상세 페이지(`document-viewer-page-sections.tsx`)에 입력값 편집 UI를 추가하는 작업은 후속 범위다. 공유 훅 변경의 회귀는 확인한다.

### 2.1 구현 전제에서 드러난 차이

1. **업무일지 지원 보완이 필요하다.** DB templateId가 있는 업무일지와 없는 문서를 구분하고, 후자도 폼 정의·서버 번들을 복원할 수 있어야 한다.
2. **Storage HTML 우선 반환은 최신 입력값을 우회할 수 있다.** 대상 양식과 유효한 입력 주석이 확인된 inline 요청은 최신 content로 서버 렌더하는 경로가 우선되어야 한다.
3. **재직증명서 자동 채움은 기존 값을 덮는다.** 현재 프로필 조회 후 `onLoaded`가 실행되어 저장 당시 인적사항이 현재 계정 정보로 교체될 수 있다. 편집 모드 정책을 분리해야 한다.
4. **휴가원 문서 수정은 휴가 원장 수정과 다르다.** 현재 PATCH는 연결 휴가 레코드·잔여일수를 동기화하지 않는다. 이 기능은 문서 입력값 편집으로 한정하고 화면에 이를 안내한다.

## 4. 화면 및 상태 흐름

1. 문서를 열면 기존 레이아웃 보기로 시작한다. 저장된 문서 정보와 선두 DOCUMENT_INPUTS를 검사해 대상 양식을 결정한다.
2. 대상 초안이면 기존 토글 옆에 `입력값 편집`을 표시한다. 주석 누락·파싱 오류·양식 판별 불가 시 진입을 비활성화하고 사유를 표시한다. 기존 열람·원문 편집은 유지한다.
3. 입력값 편집에 진입하면 **현재 편집 중인 content**의 주석을 복원한다. 생성 전용 출력 포맷·AI 보강·소스 선택·문서 구조 설정은 표시하지 않는다.
4. 필드 변경은 공용 폼의 controlled 상태를 거쳐 `buildContentWithInputs`로 `editContent`에 반영한다. 기존 `isEdited`와 닫기 확인을 그대로 사용할 수 있게 한다.
5. `레이아웃 보기`로 이동해도 미저장 입력은 유지한다. 서버 미리보기는 저장된 값 기준이며 “입력값은 초안 저장 후 레이아웃에 반영됩니다”를 표시한다.
6. 입력값 저장은 `{ content: 갱신된 content }`만 전송한다. 제목 변경이 함께 남아 있으면 입력값 저장으로 제목까지 저장된 것처럼 처리하지 않는다. 제목은 기존 저장 흐름으로 별도 저장하고 미저장 상태를 유지한다.
7. PATCH 성공 응답의 content로 `viewDoc`·목록·편집 기준을 동기화하고 서버 미리보기를 refetch한다. 실패 시 기존 저장본과 편집값을 유지한다.
8. 미리보기만 실패했다면 “입력값은 저장되었지만 미리보기를 불러오지 못했습니다”와 재시도 동작을 제공한다. 저장 실패와 구분한다.

원문 편집에서 본문을 수정한 다음 입력값 편집으로 이동했을 때도, 현재 `editContent`의 본문을 보존한다. 입력값 저장은 그 content 전체를 저장하므로 기존 본문 수정분도 함께 저장된다는 점을 안내한다. 이 기능 자체가 본문을 생성하거나 수정하지는 않는다.

## 5. 기술 요구사항

### 5.1 공용 입력폼 및 책임 분리

아래 파일명은 구현 시 사용할 제안이며, 기존 컴포넌트는 최대한 그대로 활용한다.

| 단위 | 책임 | 제외할 책임 |
| --- | --- | --- |
| `document-input-fields.tsx` (신규) | 필드 그룹·조건부 노출·양식별 UI 조합. `mode: create / edit`, 양식 정의, values, 함수형 onChange를 받는다. | API 저장, 뷰어 상태, 생성 실행, 출력 설정 |
| `TemplateFieldInput` 및 세 특수 UI | 개별 입력·선택·값 표시. 공용 폼 안에서 재사용한다. | 문서 PATCH, content 직렬화 |
| `use-document-input-autofill.ts` (신규 또는 기존 훅 확장) | 생성 초기값과 명시적 프로필 재적용 정책을 담당한다. | 마운트만으로 편집값 변경 |
| `document-input-editor.tsx` (신규) | 복원 결과·오류 표시와 공용 폼을 뷰어에 연결한다. | 전체 뷰어·다운로드 UI |
| `embedded-inputs.ts` | 주석 파싱·교체를 수행하는 순수 유틸 | React 상태, 네트워크, 양식 렌더 |
| 저장 액션 / 미리보기 훅 | content 저장과 저장 성공 후 조회를 각각 담당한다. | 필드별 UI |

- 필드 타입은 `TemplateFieldDefinition` 등 기존 공용 정의를 기준으로 맞추고 같은 인터페이스의 복제를 늘리지 않는다.
- `NewDocumentGeneralStep`은 공용 입력폼과 생성 전용 설정을 조합한다. 뷰어에서 전체 생성 step을 직접 재사용하지 않는다.
- 회의록·근로계약서 등 생성 폼의 기존 분기는 생성 전용 조합으로 유지하거나 작은 하위 컴포넌트로 분리한다. 공용화 과정에서 삭제하지 않는다.
- 생성에서는 기존 프로필·날짜·보고기간 초기화를 유지한다. 편집에서는 빈 값이라도 자동 보충하지 않고 저장된 값을 우선한다.
- 재직증명서의 `EmploymentCertAutofill`은 편집 시 저장값을 표시하는 모드를 지원한다. 기존 생성 화면의 인적사항 읽기 전용 정책을 유지하고 프로필 갱신은 명시적 재적용으로 제공한다. 누락된 필수 항목 입력은 기존 예외 정책을 유지한다.
- 휴가원은 이름만으로 직원 ID를 추론하지 않는다. 기존 문서 인적사항을 표시하고 사용자가 직원을 새로 선택할 때만 관련 필드를 바꾼다.
- 업무일지의 자동·AI 필드는 저장값을 표시하고 유지한다. 필수 수동 필드와 `showWhen` 검증 기준을 생성/편집에서 공유한다.
- 새로 만들거나 수정하는 파일은 500줄 이하를 지킨다. 기존 download route는 이미 707줄이므로 해당 보완 시 렌더 관련 책임을 유틸로 추출해 route도 제한 내로 줄인다. 무관한 로직 정리는 범위에 넣지 않는다.
- Next.js 클라이언트 경계는 설치된 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-client.md`에 맞춘다. 순수 파싱 유틸에 클라이언트 의존성을 넣지 않는다.

### 5.2 입력값 복원·교체 유틸 계약

`src/lib/documents/embedded-inputs.ts`에 다음 기능을 추가한다. 기존 두 함수의 DOCUMENT/PROPOSAL 처리 호환성은 유지한다.

**`parseEmbeddedInputs(content)`**

- 선두 `DOCUMENT_INPUTS` 주석만 신규 편집 대상으로 파싱한다. 본문 중간의 유사 주석이나 `PROPOSAL_INPUTS`를 대상 입력값으로 오인하지 않는다.
- 결과는 성공(`inputs: Record<string, string>`), 주석 없음, 손상된 주석/JSON/값 형식을 구분하는 판별 가능한 타입으로 반환한다. 정상적인 빈 객체와 파싱 실패를 구분한다.
- `null`, 배열, 원시값, 문자열이 아닌 필드 값은 오류로 취급한다. 문자열 안의 한글·줄바꿈 escape·따옴표·역슬래시는 왕복 보존한다.
- `work_rows`는 객체 배열 자체가 아니라 JSON **문자열**인 기존 계약을 유지한다. 내부 배열과 각 행의 문자열 값은 별도 검증해 손상된 행을 빈 배열로 덮어쓰지 않는다.
- 주석 없는 과거 문서나 손상된 주석은 빈 폼으로 저장하지 않는다. 본문에서 값을 추론하거나 자동 마이그레이션하지 않는다.

**`buildContentWithInputs(content, inputs)`**

- 유효한 선두 DOCUMENT_INPUTS 주석 범위만 새 JSON으로 교체한다. 주석 이후의 줄바꿈·공백·마크다운·본문 내부 주석은 원문 문자열 그대로 보존한다.
- 주석과 본문의 구분 LF/CRLF도 유지한다. `trim()`이나 광역 정규식으로 본문을 정리하지 않는다.
- 선두 주석이 없거나 손상되었거나 PROPOSAL 주석이면 오류를 반환한다. 이번 편집 기능에서 임의 접두부 추가·형식 변환은 하지 않는다.
- 기존 inputs에 수정값을 병합하고 화면에 없는 키도 유지한다. `__template_name` 등 서버 메타를 폼 필드 목록만으로 삭제하지 않는다. 빈 문자열로 지운 값은 명시적으로 저장한다.
- JSON 직렬화 결과의 `-->`를 `\u002d\u002d>` 형태로 이스케이프하여 HTML 주석의 조기 종료를 막는다. 파싱 시 원래 문자열로 복원되어야 한다.
- 무변경 진입·모드 전환만으로 JSON을 재직렬화하지 않는다. 입력값이 실제로 달라진 경우만 content를 갱신해 불필요한 수정 표시를 방지한다.

저장 구조는 `<!--DOCUMENT_INPUTS:{새 입력값 JSON}-->` 뒤에 **기존 접미 문자열 전체**를 그대로 이어 붙이는 형태다. 주석의 키 순서가 달라지더라도 본문은 달라지면 안 된다.

### 5.3 양식 식별 및 필드 정의

- 휴가원·주간업무·재직증명서는 기존 builtin resolver와 각 양식의 필드 정의를 재사용한다.
- 업무일지는 `WORKLOG_FIELDS / WORKLOG_TEMPLATE_HTML`과 기존 schema 변환을 재사용해 지원한다. templateId가 있으면 해당 정의를 확인하고, 없는 경우에도 업무일지 이름 fallback을 서버·클라이언트에 일치시킨다.
- 식별은 지원되는 templateId/템플릿 정보와 기존 이름 resolver를 우선하고, 제목 fallback은 현재 저장 구조의 호환 수단으로 사용한다. 저장된 `__template_name`이 있다면 보조 정보로 검토하되 모든 문서에 존재한다고 가정하지 않는다.
- 단순히 DOCUMENT_INPUTS가 있다는 이유로 모든 문서에 폼을 열지 않는다. 커스텀 양식의 제목만 휴가원인 경우 등 정의가 충돌하면 편집을 차단한다.
- `report_title`은 양식 내부 입력값이며 DB `title`과 구분한다. 이번 content 전용 저장은 DB 제목을 자동 변경하지 않는다. 제목 변경으로 서버 양식 식별이 실패할 수 있는 기존 한계도 확인한다.

### 5.4 저장 및 미리보기 갱신

- 기존 `csrfFetch`와 PATCH 경로를 사용한다. 입력값 저장 body는 `{ content }`이며 title·status·templateId·출력 포맷은 포함하지 않는다.
- 기존 일반 저장은 유지하되 content 전용 저장 액션을 분리하거나 저장 범위를 명시적으로 받도록 한다. 서버 성공 응답을 기준으로 저장된 content를 반영한다.
- 검증 실패·저장 중에는 입력값 저장을 막는다. 저장 중 추가 편집을 잠그거나 요청 스냅샷을 관리하여 응답이 더 최신 입력을 덮지 않도록 한다.
- `useServerRenderedPreview`의 기존 `[enabled, docId, font, content]` 의존성 재조회를 기본으로 활용한다. 성공 후 `viewDoc.content`가 바뀌면 즉시 GET을 실행한다.
- 미리보기 실패 재시도용 `refetch` 또는 동등한 재조회 트리거를 추가한다. content 갱신에 따른 자동 재조회와 명시적 refetch가 중복 호출되지 않게 한다.
- 요청은 `/api/documents/[id]/download?format=pdf&inline=true&font=...`를 사용한다. 타이핑 중에는 호출하지 않는다. 문서·폰트 전환 시 기존 AbortController 처리도 유지한다.
- 업무일지가 미리보기 대상에 포함되도록 판별을 보완한다. 서버는 유효한 대상 양식 입력값이 있으면 Storage HTML보다 최신 content 렌더를 우선한다. 기존 결재 서명·로고 적용은 유지한다.
- 원본 Storage 다운로드는 입력값 PATCH만으로 재생성되지 않는다. 이번 즉시 반영의 필수 범위는 inline 레이아웃이며, 원본 파일 다운로드까지 최신화를 보장하는 기능은 후속 과제로 분리한다. 화면 안내로 갱신 범위를 분명히 한다.
- 연결 휴가 원장·휴가 잔여일수 갱신도 별도 기능이다. “문서 입력값만 변경됩니다. 연결된 휴가 신청은 휴가 관리에서 수정하세요”를 제공한다.

## 6. 우선순위 및 구현 순서

P0는 대상 네 양식 제공 전에 모두 충족해야 하는 필수 항목이다. P1은 사용 편의, P2는 확장 과제다.

| 순서 | 우선순위 | 작업 | 완료 기준 |
| --- | --- | --- | --- |
| 1 | P0 | 파싱·교체 유틸 및 데이터 계약 확정 | 손상 데이터 차단, 본문·줄바꿈 완전 보존, 미노출 키 보존, 안전한 JSON 왕복 |
| 2 | P0 | 공용 입력폼 추출 및 자동 채움 정책 분리 | 생성/편집이 같은 입력 UI를 사용하며 편집 진입이 저장값을 바꾸지 않음 |
| 3 | P0 | 네 양식 정의·식별 통일 | 업무일지 포함, 비대상 문서와 충돌하는 정의 차단 |
| 4 | P0 | 뷰어 진입·수정 상태·content 전용 저장 | 기존 원문 편집 유지, PATCH body에 content만 포함, 실패 시 입력 유지 |
| 5 | P0 | 서버 최신 렌더와 미리보기 재조회 | 저장 성공 후 네 양식 모두 최신 입력값 표시, Storage HTML 경로 확인, 중복 호출 방지 |
| 6 | P0 | 필수 검증·오류·범위 안내·회귀 확인 | 미저장 종료 확인, 휴가 원장/원본 파일과의 차이 안내, 기존 생성 유지, 500줄 준수 |
| 7 | P1 | 명시적 프로필 재적용과 오류 재시도 UX 개선 | 기존 저장값을 유지하면서 사용자가 현재 프로필 반영 여부를 선택 |
| 8 | P2 | 원본 파일 최신화·휴가 원장 연동·상세 페이지 확장 | 별도 설계와 수용 기준을 수립한 후 진행 |
| 9 | P2 | 다른 양식 확장 및 제목 의존 식별 개선 | 품의서 등 지원 범위와 영속적인 양식 식별 계약 확정 |

## 7. 검증 및 수용 기준

구현 단계에서 다음 검증을 수행한다. 이번 기획 단계에서는 기능 코드나 테스트 코드를 추가하지 않는다.

| 구분 | 검증 항목 |
| --- | --- |
| 유틸 | 정상·빈 객체·주석 없음·깨진 JSON·배열/null/숫자 값·PROPOSAL 주석·본문 중간 주석을 구분한다. |
| 보존성 | 교체 전후 주석 이후 문자열이 완전히 같다. LF/CRLF·빈 본문·선행 공백·본문 내부 주석·주석 뒤 추가 빈 줄을 보존한다. |
| 왕복 | 한글·따옴표·역슬래시·줄바꿈·`-->`·중첩 JSON 문자열인 work_rows와 미노출 메타 키를 유지한다. |
| 생성 회귀 | 네 양식의 기존 초기값·필수값·직원 선택·인적사항 자동 채움·주간 행 UI가 동작한다. 회의록·근로계약서 등의 기존 생성도 유지된다. |
| 편집 복원 | 네 양식의 기존 값이 일치하고 프로필/기간 자동 갱신이 없다. 보기 모드 왕복만으로 수정됨이 켜지지 않는다. |
| 저장 | 네트워크 요청 body가 content 단독이다. 본문 수정 없음, 저장 후 재열기 복원, 제목 미저장 상태 보존, 403/서버 오류 시 값 유지와 재시도가 가능하다. |
| 미리보기 | PATCH 성공 후 GET이 실행되고 새 값이 표시된다. templateId 유무·Storage HTML 유무·업무일지 경로를 각각 확인한다. |
| 오류·경합 | 손상된 work_rows를 빈 배열로 저장하지 않는다. 문서 A 요청이 문서 B를 덮지 않는다. 저장 성공/미리보기 실패를 구분하고 재조회할 수 있다. |
| 기존 뷰어 | 완료 상태 편집 제한, 미저장 닫기 확인, 원문 편집 시 주석 유지, 제안서/커스텀 템플릿 미리보기, 공유 훅 사용 화면에 회귀가 없다. |
| 구조 | 추가·수정 파일 500줄 이하, 폼·자동 채움·저장·파싱·렌더 책임 분리, 변경 범위에 맞는 타입 검사·린트 통과. |

출시 기준은 네 양식 모두에서 **복원 → 입력값 변경 → content 단독 저장 → 최신 서버 레이아웃 확인 → 재열기 복원**이 성립하는 것이다. 업무일지나 Storage HTML 문서에서 이 흐름이 실패하면 P0 미완료로 판단한다.
